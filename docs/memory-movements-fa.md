# FlashAttention Memory Movements and Cache Notes

This note summarizes the sliding paged decode attention memory traffic and the
cache choices worth testing next. It focuses on the current direct-load decode
path; the old decode `cp.async` ablation has been removed from active code.

| Memory movement / operation | Detailed description | Cache policy / recommendation |
| --- | --- | --- |
| Q prepared load | Each split CTA owns one batch row, one KV head, and the two query heads in its GQA group. Every thread loads one BF16 lane from each of the two prepared Q vectors, then reuses those two scalar Q values for all keys in the split. | Keep as read-only global loads. Q is tiny per CTA and reused from registers, so there is no reason to stage it in shared memory. |
| Sequence length load | Each split and reduce CTA loads `seq_lengths[batch]` to compute the sliding-window `first_key`, `key_count`, and actual live split count. | Keep as `__ldg`/read-only. This is one scalar per CTA, so constant memory is not necessary unless sequence metadata becomes broadcast-heavy across many kernels. |
| Page table load | The hot loop maps each logical position to a page slot, then loads the physical page from `page_table[batch * max_pages_per_seq + slot]`. With `split_size=64` and `page_size=64`, many positions share the same page table entry. | Strong candidate for page-chunking. Load the page table once per page tile, then walk page offsets linearly. The cache policy can stay read-only; the bigger win is reducing repeated address math and scalar page-table loads. |
| Page offset calculation | The current loop derives `page_slot` and `page_offset` per token. When page size is runtime data, modulo/division lowers to multiple integer instructions. | Avoid modulo in the inner token loop by iterating page spans. If page size remains fixed at 64 for the target path, specialize it as a power-of-two mask/shift. |
| K cache vector load | For each valid token position, all 256 threads load one BF16 K lane for the selected KV head. The access is contiguous across the head dimension and naturally coalesced. | Keep direct read-only global loads for now. The measured decode `cp.async` staging path was slower because it performed an immediate wait and added shared-memory traffic/barriers. |
| V cache vector load | Same address shape as K: all 256 threads load one BF16 V lane for the selected KV head, then each thread uses its lane for the online accumulator. | Keep direct read-only global loads. Revisit only if a future design overlaps page/tile prefetch with dot-product work rather than immediately waiting. |
| GQA K/V reuse | One CTA computes two query heads for one KV head, so each K/V vector load feeds both Q-head score paths and both value accumulators. | Preserve this grouping. It is the main useful decode cache reuse in the CUDA-core path. |
| CUB score reductions | Each token computes two block-wide reductions, one for each query head dot product. The kernel now uses separate CUB temp storage for the two reductions. | Keep separate temp storage. Reusing CUB temp storage is easy to make unsafe without a clear synchronization boundary, and separate storage lets the two logical reductions stay unambiguous. |
| Partial `m`/`l` stores | Each live split writes one `m` and `l` scalar per query head. Empty overprovisioned split CTAs now return without neutral writes. | Keep uncached ordinary global stores. These values are consumed immediately by the reduce kernel, but they are small and contiguous by row/split. |
| Partial accumulator stores | Each live split writes `head_dim` FP32 accumulator values per query head. This is the largest scratch write. | Keep layout as `[batch, q_head, split, dim]` for coalesced per-row reduction. Avoid writing dead overprovisioned splits, as implemented. |
| Reduce kernel partial reads | The reducer reads only `actual_splits` per batch row while keeping `num_splits` as the scratch stride. It reads `partial_m`, `partial_l`, and `partial_acc` for live splits only. | Keep direct global reads. If split count grows, consider vectorized accumulator loads or reducing split count via larger split size before adding cache machinery. |
| Final output store | Each reduce CTA writes one BF16 attention output row `[q_head, dim]`. Threads write contiguous BF16 lanes. | Ordinary global stores are fine. The output should remain projection-ready; avoid extra packing passes. |
| Invalid page guard | Each token checks whether the physical page is valid before loading K/V. Valid decode paths should almost always pass this guard. | Keep the guard for correctness. A production launcher with validated page tables could later add a fast path without the branch. |
| Overprovisioned split CTAs | Fixed graph-compatible launches may use a max `num_splits` even when a row has fewer live splits. Those CTAs now return before touching scratch. | Keep this. It preserves graph shape while avoiding neutral scratch writes and reduce reads. |
| L2 behavior across repeated benches | Reusing the same cache buffers measures warm-L2 behavior unless explicitly flushed. | Continue reporting warm/cold cache separately. For cold decode traffic, flush L2 with a buffer larger than GPU L2 and record the flush size. |
